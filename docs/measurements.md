# 마일스톤별 측정 기록

메모리 최소화가 제1 요구사항이므로(설계서 §4-5) 마일스톤마다 아래 값을 기록한다.
게이트를 넘으면 기능 추가를 멈추고 원인부터 잡는다.

| 항목 | 목표 | 근거 |
|---|---|---|
| 번들 크기 | 30MB 이하 | NFR-01 |
| 상주 메모리 (창 0개) | 50MB 이하 | NFR-09 |
| 메모 10개 표시 | 120MB 이하 (스펙 150MB보다 엄격한 내부 목표) | NFR-02 |
| 창 닫은 후 회수 | 본문·이미지 메모리 해제 | NFR-10 |

측정 방법: `make mem` (RSS 기준) 또는 메뉴바 → 메모리 항목(phys_footprint 기준).
RSS는 공유 라이브러리를 포함하므로 실제 앱 점유량보다 크게 잡힌다.

---

## M0 — 골격 (2026-08-26)

| 항목 | 측정값 | 판정 |
|---|---|---|
| 번들 크기 | 404KB | 통과 (목표 30MB) |
| 상주 메모리 (창 0개) | 47.7MB RSS | 통과 (목표 50MB) |
| 메모 10개 표시 | 65.7MB RSS | 통과 (목표 120MB) |
| 창 1개당 증가분 | 약 1.8MB | — |
| 창 닫은 후 회수 | 미측정 | M1로 이월 |

확인된 동작:

- 창 레이어 3(floating) — 항상 위 표시가 실제로 적용됨 (WIN-03)
- `alphaValue = 1.0` 유지 — 투명도는 배경 레이어와 텍스트에만 적용 (설계서 §3 원칙)
- 창 크기 300×320으로 생성, 겹치지 않게 어긋나 배치

메모: 창 0개 상태의 47.7MB는 AppKit·Swift 런타임 등 공유 라이브러리가 대부분이다.
창 하나당 실제 증가분(약 1.8MB)이 앞으로 관리할 값이며, M1에서 본문·서식이 들어가면
이 수치가 어떻게 변하는지가 관건이다.

## M1 — 저장 · 실시간 변환 (2026-08-26)

| 항목 | 측정값 | 판정 |
|---|---|---|
| 번들 크기 | 704KB | 통과 (목표 30MB) |
| 상주 메모리 (메모 10개 보유, 창 0개) | 48.1MB | 통과 (목표 50MB) |
| 메모 10개 표시 (각 10줄, 현실 분량) | 90.1MB | 통과 (목표 120MB) |
| 메모 10개 표시 (각 60줄, 과부하) | 119.0MB | 경계 — 아래 메모 참고 |
| 메모 3개 표시 (각 60줄) | 96.7MB | — |
| 한글 IME 수동 테스트 | 미실시 | [manual-test-ime.md](manual-test-ime.md) 로 확인 필요 |

**지연 로드가 작동한다는 증거**: 메모 10개를 보유하고도 창을 하나도 열지 않으면 48.1MB로,
메모가 없던 M0의 47.7MB와 사실상 같다. 메모 수가 늘어도 상주 메모리는 늘지 않는다.

**창당 비용의 구조**: 첫 창에서 약 40MB가 한 번에 늘고(AppKit 텍스트 시스템과 글꼴 변형 적재),
그 뒤로는 창 하나에 약 3.2MB씩 붙는다. 즉 창을 많이 띄우는 것보다 첫 창을 여는 순간이 비싸다.

**과부하 조건의 경계값**: 메모당 60줄씩 10개를 동시에 띄우면 119MB로 내부 목표(120MB)에 닿는다.
스펙 기준(NFR-02, 150MB)은 통과하지만 여유가 없다. 실사용 분량(10줄)에서는 90MB로 문제가 없으므로
지금 최적화하지는 않되, M2에서 창 기능이 늘 때 이 수치를 다시 재고 넘어가면 그때 잡는다.
후보: 화면 밖 창의 레이아웃 매니저 해제, 긴 본문의 지연 레이아웃.

**미확인**: 창을 닫았을 때의 메모리 회수(NFR-10)는 메뉴 클릭이 필요해 자동 측정하지 못했다.
설계상 컨트롤러가 해제되면 본문도 함께 사라지지만, M2에서 창 조작을 자동화해 확인한다.

## M4 — iCloud 스냅숏 동기화 (2026-08-26)

| 항목 | 결과 |
|---|---|
| 번들 크기 | 2.1MB (목표 30MB) |
| 실제 iCloud Drive로 올리기 | 확인 — `~/Library/Mobile Documents/com~apple~CloudDocs/MemoApp/memos/` |
| 실제 iCloud Drive에서 내려받기 | 확인 — 다른 기기가 올린 것처럼 심어 둔 메모가 로컬로 들어옴 |
| 열린 창 미러링 (SYNC-08) | 확인 — 내려받은 메모의 `open: true`가 창으로 이어짐 |

**두 기기 시험 방법**: 실제로 맥 두 대를 놓고 시험할 수 없으므로,
폴더 세 개(맥미니·맥북·그 사이 iCloud)로 흉내 내는 자동 테스트를 만들었다.
새 메모 전달, 수정 반영, 동시 수정 충돌, 삭제 전파, 열린 상태 공유, 그룹 합치기를
모두 이 방식으로 확인한다 (Services 테스트 9개).

**충돌 처리 확인**: 양쪽에서 같은 메모를 고치면 최신본이 정본으로 남고
진 쪽은 새 ID를 붙인 사본으로 보존된다. 사본에는 `conflictOf`가 적혀
리스트 창에 "충돌 사본" 표시가 붙는다. 어느 쪽 내용도 사라지지 않는다.

## M2 — 스티키 창 완성 (2026-08-26)

| 항목 | 측정값 | 목표 |
|---|---|---|
| 번들 크기 | 2.0MB | 30MB |
| 메모 2개 표시 | 80.0MB | — |

겉모습 패널(배경색·투명도)은 열 때 만들고 닫으면 버린다.
창마다 상주시키면 창 수만큼 메모리가 붙는다.

**NFR-10(창 닫으면 메모리 회수) 확인**: 그동안 메뉴 클릭이 필요해 미뤄 뒀는데,
창 조작을 코드로 부를 수 있게 열면서 자동 테스트로 확인했다 —
창을 닫으면 컨트롤러가 목록에서 사라진다(= 본문이 메모리에서 풀린다).

## M3 — 리스트 창 (2026-08-26)

| 항목 | 측정값 | 목표 | 판정 |
|---|---|---|---|
| 검색 (메모 1,000개, 본문 전체) | 0.3초 이내 | 0.3초 (NFR-05) | 통과 |
| 상주 메모리 (메모 1,000개 보유, 창 0개) | 51.6MB | 50MB (NFR-09) | 경계 |
| 리스트 창 열었을 때 (메모 1,000개) | 93.3MB | — | |
| 리스트 창 열었을 때 (메모 4개) | 87.0MB | — | |

**검색 방식**: SQLite 인덱스를 넣지 않고, 제목·미리보기로 먼저 거른 뒤
걸리지 않은 메모만 파일을 열어 본문을 확인한다. 읽은 내용은 즉시 버린다.
1,000개 기준으로 목표를 만족하므로 인덱스 도입은 미뤘다.
메모가 수천 개로 늘어 이 수치가 나빠지면 그때 DOC-03(SQLite FTS5)을 넣는다.

**상주 51.6MB에 대해**: 메모가 하나도 없을 때 48.1MB이므로 1,000개의 요약이
3.5MB를 차지한다. 목표(50MB)를 조금 넘지만, 이는 메모 1,000개라는 극단적인 경우이고
요약 하나당 3.5KB 수준이라 설계대로 동작하고 있다.
줄이려면 미리보기 길이(현재 200자)를 줄이면 된다 — 필요해지면 그때 조정한다.

**리스트 창은 닫으면 통째로 해제한다**: 창과 모델을 함께 버려, 열지 않은 동안에는
목록 화면이 메모리를 차지하지 않는다.

M5 예정이던 슬래시 명령(SL-*)과 목록 조작을 앞당겨 넣은 뒤 다시 측정했다.

## v0.10.1 - 목록 보기 전환 속도 · 메모리 (2026-11-25)

메모 300개(체크박스·연결 포함) 시험 폴더로 릴리스 빌드를 띄우고, 보기를 그리드 → 벤토 → 보드 → 목록 순서로 4바퀴 바꿨다.
`--data-dir`로 띄운 개발 실행에서만 받는 알림으로 보기를 바꿔, 손쉬운 사용 도구가 끼지 않게 쟀다(손쉬운 사용 도구가 붙으면 SwiftUI가 접근성 트리를 갱신하느라 몇 배 느려진다).
값은 전환 한 번에 쓴 CPU 시간과 그 뒤의 phys_footprint다.

| 보기 | v0.10.0 CPU | v0.10.1 CPU | v0.10.0 메모리 | v0.10.1 메모리 |
|---|---|---|---|---|
| 그리드 | 60ms | 50ms | 129~340MB | 60~74MB |
| 벤토 | 1,280ms | 50ms | 329~533MB | 61~74MB |
| 보드 | 1,060ms | 80ms | 241~563MB | 71~74MB |
| 목록 | 230ms | 70ms | 193~462MB | 73~76MB |

고친 것:
- 벤토가 카드 300장을 한꺼번에 만들던 것을, 카드가 걸치지 않는 행 경계로 띠를 나눠 `LazyVStack`으로 보이는 띠만 만들게 했다.
- 보드는 축소 비율 0.55 아래에서 카드를 SwiftUI 뷰 대신 배경 캔버스에 그린다. 마우스 올림 상태를 카드 안으로 옮겨 보드 전체가 다시 그려지지 않게 했다.
- 보드 배경 점 격자가 멀리서 볼 때 간격 2px 남짓으로 좁아져 점을 14만 개쯤 그리던 것을, 화면에서 16pt보다 좁아지면 격자를 두 배씩 성기게 했다. 메모리가 크게 늘던 주원인이었다.
- 날짜 포매터와 미리보기 정규식을 한 번만 만들고, 카드 미리보기 · 체크리스트 · 벤토 크기 · 보이는 메모 목록을 캐시해 바뀐 메모만 다시 계산한다.

## P1 Rust 연결 (2026-11-26)

브랜치 전환 없이 main `8e83351`과 변경 전 HEAD `de4070d`의 추적 파일을 별도 복사해
각각 `make release`로 다시 빌드했다. 과거의 약 15M 기록 대신 이번 측정값을 기준으로 한다.
세 빌드 모두 arm64와 x86_64 유니버설이며 같은 Xcode 27.0과 동일한 선택적 OAuth 리소스를 사용했다.
번들은 `du -sk`의 디스크 점유량, 실행 파일은 `stat -f %z`의 바이트 수다.

| 대상 | main 재측정 | P1 직전 HEAD | P1 Rust 연결 후 |
|---|---:|---:|---:|
| 앱 번들 | 16,952 KiB (16.55 MiB) | 16,932 KiB (16.54 MiB) | 17,812 KiB (17.39 MiB) |
| 실행 파일 | 16,689,760 바이트 | 16,669,904 바이트 | 17,568,304 바이트 |

main 대비 번들은 860 KiB, 실행 파일은 878,544 바이트 증가했다.
P1 직전 HEAD 대비 번들은 880 KiB, 실행 파일은 898,400 바이트 증가했다.
모든 번들은 30MB 목표 이하다. 앱은 실행하지 않았다.

샌드박스에서 SwiftPM 내부 sandbox 실행과 외장 볼륨 중간 파일 쓰기가 막혀,
검증용 래퍼로 `--disable-sandbox`, 내부 임시 빌드 경로와 저장소 안 모듈 캐시를 지정했다.
유니버설 빌드의 dSYM 생성도 제한되어 세 빌드에 동일하게 `-debug-info-format none`을 사용했다.
이 래퍼는 `build/`의 검증 산출물이며 제품 빌드 스크립트는 변경하지 않았다.
Windows 검증은 기존 cargo-xwin 캐시를 `build/xwin-cache`로 복사하고 `XWIN_CACHE_DIR`로 지정했다.

검증 결과:

- `make build`, `make release`, Windows MSVC 교차 release 빌드를 포함한 `make check` 성공.
- Rust 작업공간 테스트 통과, CoreBridgeTests 2개 통과, Swift 골든 15개 바이트 일치.
- `make test`의 Swift 러너는 360개 통과, MemoCore 1개 실패로 명령 전체는 실패.
- 실패는 백업 제외 속성 검사로, 변경 전 HEAD의 MemoCore 러너에서도 88개 통과와 같은 1개 실패를 확인했다. `isExcludedFromBackup`이 기대값 `true` 대신 `false`다.
- release 지문 캐시의 재실행 건너뛰기와 staticlib의 arm64, x86_64 포함을 확인했다.

## P5 입력 규칙 지연 (2026-11-26)

계획표 기준: 키 입력 1회의 FFI 왕복이 0.2ms 이하일 때만 입력 규칙을 Rust로 옮긴다.
`Scripts/measure-input-rule.sh`가 Rust를 release로 빌드하고 `CoreBridgeTests`를 release로 돌려 잰다
(`Packages/CoreBridge/Tests/CoreBridgeTests/main.swift`의 `MDEMO_MEASURE=1` 경로).
대표 줄 200개(평범한 글을 한 글자씩 치는 줄, 줄머리 기호 직후, 닫는 기호 직후, 줄 중간 커서, 이모지 · 결합 문자 줄)를 1,000회씩, 20만 호출이다.
평균은 전체 시간을 호출 수로 나눈 값이고, p99와 최대는 호출마다 시계를 읽어 잰 값이다(시계 호출 비용 약 0.04us 포함).
Swift 직접 호출은 `InputRuleSet.m1.firstMatch`, FFI는 `InputRuleBridge.firstMatch`(UniFFI 문자열 · 레코드 변환 포함)다.
측정 환경: Apple M4, macOS 26.6.2, release 빌드(Rust는 lto, opt-level s). 결과 일치는 같은 시험에서 200줄 모두 확인했다.

| 구현 | 호출 수 | 평균 | p99 | 최대 |
|---|---:|---:|---:|---:|
| Swift 직접 호출 | 200,000 | 3.71 us | 11.17 us | 112.7 us |
| Rust FFI 왕복 | 200,000 | 9.76 us | 33.50 us | 95.2 us |
| (참고) 빈 FFI 호출 `ping` | 200,000 | 0.00 us | 0.04 us | 0.1 us |

판단: **이전 가능.** FFI 왕복은 평균 0.0098ms, p99 0.034ms, 최대 0.095ms로 기준 0.2ms의 5%, 17%, 48%다.
Swift 직접 호출보다 평균 약 6us 느리지만 키 입력 한 번의 예산에 비하면 무시할 수 있다.
느려진 몫은 호출 고정 비용(0.00us)이 아니라 줄의 문자소 나누기와 문자열 변환이다. 앱 연결은 P7에서 한다.
한계: 한 줄이 수천 자인 경우와 하위 macOS의 Intel 기기에서는 재지 않았다. 이 경우를 확인하려면 같은 스크립트로 줄 목록을 바꿔 다시 잰다.

## P7 저장소 그림자 실행 (2026-11-26)

`MemoCoreTests --shadow-tests-only`의 저장 측정은 시험용 임시 APFS 폴더와 메모리 키체인만 사용한다. UTF-8 한글 본문 200줄(약 2.6KB), 첨부 없는 기존 메모를 먼저 만들고, Swift 직접 저장과 그림자 저장을 번갈아 30회 실행했다. 각 회차에서 백그라운드 비교를 비운 다음 다음 회차를 시작한다. 측정값은 두 저장의 동기 호출 시간 차이이며 Rust 비교·해시·기록 완료 대기는 제외한다. 단독 실행한 한 회차는 중앙값 **3.38ms**, p95 **3.64ms**, 최대 **3.76ms**였다. 이 회차는 5ms 목표 이하다. 전체 시험 안의 이전 실행은 중앙값 3.25ms, p95 4.58ms, 최대 4.94ms였다.

최신 전체 시험에서는 중앙값 3.98ms, p95 5.34ms, 최대 6.48ms였다. 이후 부분 시험은 중앙값 3.56ms, p95 9.65ms, 최대 9.89ms였고, 최종 보강 뒤 재검사는 중앙값 3.67ms, p95 4.16ms, 최대 4.44ms였다. 동시 빌드와 암호 시험 중에는 중앙값 10.34ms, p95 24.38ms까지 올라갔다. 중앙값은 통상 5ms 이하지만 p95·최대의 5ms 목표는 일관되게 충족하지 못했다. 이 값도 숨기지 않는다. 첨부가 많거나 큰 메모, 다른 볼륨, 느린 파일시스템의 5ms는 보장하지 않는다. 앱은 실행하지 않았고 실제 데이터 저장 성능도 측정하지 않았다. 동기 경로는 두 복제와 잠금 헤더·링크·용량 검사만 포함하며, 백그라운드 Rust 작업의 잠금을 기다리지 않는다.

그림자 기능은 기본 꺼짐이며 해당 경로에서는 기존 Swift 저장소 값을 그대로 반환한다. 복제 용량 500MiB와 대기 비교 200건의 상한, 읽기 변경 재검사, 요약 한 시간 제한, 1µs mtime 경계를 시험했다. 자동 mtime 엄격 비교 때문에 정상 쓰기도 `diff`로 기록될 수 있으며, 쓰기 전체 `same` 조건은 아직 충족하지 않는다. 현재 Swift ISO8601 날짜는 일부 소수부를 읽고 다시 쓸 때 1ms 낮아지는 경우도 관찰했다(예: `.134Z`에서 `.133Z`). 실제 시계를 쓰던 초기 그림자 시험에서 이 차이를 잡았으며 기준 구현을 보정하지 않았다. 동작 시험의 시각은 정확히 표현 가능한 고정 `.125`초를 사용한다.

검증 실행에서 SwiftPM 중첩 sandbox와 빌드 서비스의 환경 제약을 피하기 위한 옵션은 `build/p7-tools/swift`의 임시 실행 래퍼에만 주입했다. 모듈 캐시는 임시 폴더, Windows SDK 캐시는 기존 `build/xwin-cache` 복사본을 사용했다. 배포·빌드 스크립트에는 우회 옵션을 추가하지 않았다.

## P7 2-d 실제 마크다운 뒷단 (2026-11-27)

`Scripts/measure-input-rule.sh`는 이제 MemoCore의 `MarkdownBackendTests.swift`에서 측정한다. CoreBridge는 MarkdownEngine에 의존하지 않는다. 인자 없이 실행하면 Swift 뒷단, `--rust-markdown`을 넘기면 Rust 뒷단이 설치된 공개 진입점도 측정한다. 임시 설정 홈만 사용하며 저장소 · 키체인 · 네트워크 · 앱 실행은 필요 없다.

환경은 macOS 26.6.2 arm64, Swift와 Rust 모두 release다. 최종 측정은 전체 시험과 빌드를 마친 뒤 실행했다. 대표 줄 200개를 1,000회 호출하고 별도로 같은 횟수의 호출마다 시간을 재어 p99 · 최대를 구했다. 예열을 포함하며 평균은 전체 루프 시간에서 구한다. 공개 `InputRuleSet.m1` 값은 규칙 목록 생성, 뒷단 선택, 규칙 기술자 변환, UniFFI 왕복까지 포함한다. 표의 두 공개 진입점은 뒷단별 별도 프로세스에서 측정했다.

| 입력 규칙 경로 | 호출 수 | 평균 | p99 | 관측 최대 |
|---|---:|---:|---:|---:|
| 공개 InputRuleSet.m1, Swift 설치 | 200,000 | 4.48 us | 11.75 us | 79.1 us |
| 공개 InputRuleSet.m1, Rust 설치 | 200,000 | 12.13 us | 36.00 us | 1,877.5 us |
| SwiftMarkdownBackend 직접 호출, Rust 설치 프로세스 | 200,000 | 3.44 us | 10.25 us | 6,486.9 us |
| RustMarkdownBackend 직접 호출, 같은 프로세스 | 200,000 | 10.88 us | 34.83 us | 970.8 us |

Rust 공개 경로의 평균 0.01213ms · p99 0.036ms는 0.2ms 목표 이하다. 다만 관측 최대는 1.8775ms로 목표를 넘었다. 다른 빌드를 함께 돌리지 않았지만 시계로 잰 개별 호출에는 실행 중단 시간도 포함된다. 이 결과로 모든 호출이 0.2ms 이내라고 보장할 수 없다. P5의 문단 전용 FFI와 달리 새 경로는 현재 블록, 임의 기호, 규칙 순서와 64비트 서식도 전달한다.

문서는 제목 · 한글 · 이모지 · 결합 문자 · 굵게 · 목록 · 표가 섞인 문자열을 Character 기준 정확히 10,000자로 잘랐다. 두 뒷단의 전체 StyledLine 결과가 같은지 먼저 확인하고 예열한 뒤, 순서를 번갈아 각 100회 파싱했다. 아래는 Rust 뒷단을 설치한 한 프로세스 안에서 직접 뒷단 두 개를 비교한 값이다. Rust에는 UniFFI 문자열 · 레코드 변환이 포함되며, 두 직접 호출 모두 공개 선택 잠금만 제외한다.

**문서 parse는 Swift 대비 +10% 이내 목표에 미달한다.** Swift 설치 프로세스의 별도 측정도 Swift 3.343ms, Rust 6.755ms로 +102.1%였다. 기능 전환과 결과 일치는 확인했으나 문서 파싱 성능 목표를 달성했다고 보지 않는다. 원인별 분해 측정과 최적화는 이번 작업에서 하지 않았다.
