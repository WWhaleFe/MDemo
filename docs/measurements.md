# 마일스톤별 측정 기록

메모리 최소화가 제1 요구사항이므로(설계서 §4-5) 마일스톤마다 아래 값을 기록한다.
게이트를 넘으면 기능 추가를 멈추고 원인부터 잡는다.

| 항목 | 목표 | 근거 |
|---|---|---|
| 번들 크기 | 30MB 이하 | NFR-01 |
| 상주 메모리 (창 0개) | 50MB 이하 | NFR-09 |
| 메모 10개 표시 | 120MB 이하 (스펙 150MB보다 엄격한 내부 목표) | NFR-02 |
| 창 닫은 후 회수 | 본문·이미지 메모리 해제 | NFR-10 |

측정 방법: `make mem` (RSS 기준) 또는 메뉴바 → 메모리 항목(phys_footprint 기준).
RSS는 공유 라이브러리를 포함하므로 실제 앱 점유량보다 크게 잡힌다.

---

## M0 — 골격 (2026-08-26)

| 항목 | 측정값 | 판정 |
|---|---|---|
| 번들 크기 | 404KB | 통과 (목표 30MB) |
| 상주 메모리 (창 0개) | 47.7MB RSS | 통과 (목표 50MB) |
| 메모 10개 표시 | 65.7MB RSS | 통과 (목표 120MB) |
| 창 1개당 증가분 | 약 1.8MB | — |
| 창 닫은 후 회수 | 미측정 | M1로 이월 |

확인된 동작:

- 창 레이어 3(floating) — 항상 위 표시가 실제로 적용됨 (WIN-03)
- `alphaValue = 1.0` 유지 — 투명도는 배경 레이어와 텍스트에만 적용 (설계서 §3 원칙)
- 창 크기 300×320으로 생성, 겹치지 않게 어긋나 배치

메모: 창 0개 상태의 47.7MB는 AppKit·Swift 런타임 등 공유 라이브러리가 대부분이다.
창 하나당 실제 증가분(약 1.8MB)이 앞으로 관리할 값이며, M1에서 본문·서식이 들어가면
이 수치가 어떻게 변하는지가 관건이다.

## M1 — 저장 · 실시간 변환 (2026-08-26)

| 항목 | 측정값 | 판정 |
|---|---|---|
| 번들 크기 | 704KB | 통과 (목표 30MB) |
| 상주 메모리 (메모 10개 보유, 창 0개) | 48.1MB | 통과 (목표 50MB) |
| 메모 10개 표시 (각 10줄, 현실 분량) | 90.1MB | 통과 (목표 120MB) |
| 메모 10개 표시 (각 60줄, 과부하) | 119.0MB | 경계 — 아래 메모 참고 |
| 메모 3개 표시 (각 60줄) | 96.7MB | — |
| 한글 IME 수동 테스트 | 미실시 | [manual-test-ime.md](manual-test-ime.md) 로 확인 필요 |

**지연 로드가 작동한다는 증거**: 메모 10개를 보유하고도 창을 하나도 열지 않으면 48.1MB로,
메모가 없던 M0의 47.7MB와 사실상 같다. 메모 수가 늘어도 상주 메모리는 늘지 않는다.

**창당 비용의 구조**: 첫 창에서 약 40MB가 한 번에 늘고(AppKit 텍스트 시스템과 글꼴 변형 적재),
그 뒤로는 창 하나에 약 3.2MB씩 붙는다. 즉 창을 많이 띄우는 것보다 첫 창을 여는 순간이 비싸다.

**과부하 조건의 경계값**: 메모당 60줄씩 10개를 동시에 띄우면 119MB로 내부 목표(120MB)에 닿는다.
스펙 기준(NFR-02, 150MB)은 통과하지만 여유가 없다. 실사용 분량(10줄)에서는 90MB로 문제가 없으므로
지금 최적화하지는 않되, M2에서 창 기능이 늘 때 이 수치를 다시 재고 넘어가면 그때 잡는다.
후보: 화면 밖 창의 레이아웃 매니저 해제, 긴 본문의 지연 레이아웃.

**미확인**: 창을 닫았을 때의 메모리 회수(NFR-10)는 메뉴 클릭이 필요해 자동 측정하지 못했다.
설계상 컨트롤러가 해제되면 본문도 함께 사라지지만, M2에서 창 조작을 자동화해 확인한다.

## M2 — 스티키 창 완성 (2026-08-26)

| 항목 | 측정값 | 목표 |
|---|---|---|
| 번들 크기 | 2.0MB | 30MB |
| 메모 2개 표시 | 80.0MB | — |

겉모습 패널(배경색·투명도)은 열 때 만들고 닫으면 버린다.
창마다 상주시키면 창 수만큼 메모리가 붙는다.

**NFR-10(창 닫으면 메모리 회수) 확인**: 그동안 메뉴 클릭이 필요해 미뤄 뒀는데,
창 조작을 코드로 부를 수 있게 열면서 자동 테스트로 확인했다 —
창을 닫으면 컨트롤러가 목록에서 사라진다(= 본문이 메모리에서 풀린다).

## M3 — 리스트 창 (2026-08-26)

| 항목 | 측정값 | 목표 | 판정 |
|---|---|---|---|
| 검색 (메모 1,000개, 본문 전체) | 0.3초 이내 | 0.3초 (NFR-05) | 통과 |
| 상주 메모리 (메모 1,000개 보유, 창 0개) | 51.6MB | 50MB (NFR-09) | 경계 |
| 리스트 창 열었을 때 (메모 1,000개) | 93.3MB | — | |
| 리스트 창 열었을 때 (메모 4개) | 87.0MB | — | |

**검색 방식**: SQLite 인덱스를 넣지 않고, 제목·미리보기로 먼저 거른 뒤
걸리지 않은 메모만 파일을 열어 본문을 확인한다. 읽은 내용은 즉시 버린다.
1,000개 기준으로 목표를 만족하므로 인덱스 도입은 미뤘다.
메모가 수천 개로 늘어 이 수치가 나빠지면 그때 DOC-03(SQLite FTS5)을 넣는다.

**상주 51.6MB에 대해**: 메모가 하나도 없을 때 48.1MB이므로 1,000개의 요약이
3.5MB를 차지한다. 목표(50MB)를 조금 넘지만, 이는 메모 1,000개라는 극단적인 경우이고
요약 하나당 3.5KB 수준이라 설계대로 동작하고 있다.
줄이려면 미리보기 길이(현재 200자)를 줄이면 된다 — 필요해지면 그때 조정한다.

**리스트 창은 닫으면 통째로 해제한다**: 창과 모델을 함께 버려, 열지 않은 동안에는
목록 화면이 메모리를 차지하지 않는다.

## M1 마무리 — 슬래시 명령·목록 조작 추가 후 (2026-08-26)

M5 예정이던 슬래시 명령(SL-*)과 목록 조작을 앞당겨 넣은 뒤 다시 측정했다.

| 항목 | 측정값 | 목표 | 비교 |
|---|---|---|---|
| 번들 크기 | 1.2MB | 30MB | M1 초기 704KB |
| 상주 메모리 (창 0개) | 48.1MB | 50MB | M1 초기 48.1MB — 변화 없음 |
| 메모 10개 표시 | 83.2MB | 120MB | M1 초기 90.1MB보다 낮음 |

기능이 늘었는데 메모리가 늘지 않은 이유는 두 가지다.
슬래시 팝업은 쓸 때 만들고 닫을 때 버리며, 글꼴 목록도 메뉴를 실제로 열 때만 만든다.
한때 글꼴 목록을 시작할 때 만들어 27MB가 더 들었는데(설치 글꼴을 전부 열어 검사),
지연 생성으로 되돌렸다.
