# 숨은 동작의 Swift 기준선

기준은 `docs/rust-transition.md`의 P0-2와 요청에 포함된 계획표 요약이다. 아래 이름은 TestKit 러너에 등록된 실제 테스트 이름이다. 이미 있던 테스트는 재사용했고 부족한 경계만 추가하거나 기존 검증을 보강했다. 구현 동작은 바꾸지 않았다.

## 요약과 실제 코드가 다른 부분

- `FileMemoRepository.saveBoardLayout`은 현재 `prettyPrinted + sortedKeys`다. 입력 객체 키 순서를 보존하지 않는다. 동작을 바꾸지 않고 현재 정렬 순서를 테스트했다.
- groups.json은 문자열 배열이다. 저장기는 `prettyPrinted`만 사용하고 배열의 원래 순서를 보존한다. 객체가 없으므로 `sortedKeys`의 효과도 없다.
- CRLF는 LF로 바뀐다. 본문의 단독 CR은 보존하지만 프론트매터 전체를 단독 CR로 구분한 파일은 현재 읽지 못한다.
- NaN은 알파 하한으로 치환되지 않고 남으며 프론트매터에는 `nan`으로 기록된다. 하한 동작은 유한 숫자에 적용된다.
- 시각 비교는 `Date.timeIntervalSince1970`의 Double로 수행한다. ±0.0005 같은 십진 경계는 Date 저장과 epoch 변환에서 표현 가능한 인접 값으로 반올림될 수 있다. 테스트는 입력 여섯 개와 실제 Double 경계를 모두 확인한다. 2001 epoch에서 ±0.0005초를 더한 값은 1970 epoch 변환 후 약 ±0.000499964초가 되어 현재 같은 순간으로 판정된다. 외부 편집의 실제 Double 경계와 바로 다음 표현 가능한 값도 별도로 확인한다. Rust도 십진수 기반의 임의 오차 보정으로 바꾸면 안 된다.
- 동기화 상태 JSON은 2001 기준 초 숫자를 사용한다. 지문 채택은 허용 오차 없이 Date의 정확한 동등 비교를 사용한다. 외부 편집 및 같은 순간 판정의 허용 오차와 별개다.

## P3에서 찾은 저장소의 숨은 동작

Rust 저장소(`mdemo-core::store`)를 Swift와 맞추며 확인한 동작이다. 시나리오 `golden/scenarios/`와 Rust 단위 테스트로 고정했다.

- 목록 읽기는 파일 앞 8KB만 읽고, 닫는 구분자 `---` 줄이 둘 미만이면 전체를 읽는다. 구분자 줄은 가로 공백만 걷어 세므로 CRLF 파일은 줄 끝 CR 때문에 하나도 세어지지 않아 항상 전체를 읽는다.
- 8KB 경계가 UTF-8 문자 한가운데에 걸리면 뒤에서 최대 3바이트를 덜어 다시 해석한다. 이 경우에는 구분자를 다시 세지 않고 앞부분만 쓰므로, 앞머리가 8KB보다 길면 그 메모는 목록에서 빠진다.
- 저장은 폴더를 먼저 만들고 파기 장부를 본다. 파기된 ID를 저장하면 오류가 나지만 빈 `memos/<ID>` 폴더가 남는다. 이때 `MemoStore.createMemo`는 저장 실패를 무시하고 요약을 목록과 보드 직접 순서에 넣고, 다음에 목록을 다시 읽을 때 빠진다.
- 휴지통 폴더가 이미 있으면 지우고 덮어쓴다. 복원 자리에 같은 ID가 있으면 복원하지 않고 오류도 없이 휴지통에 남긴다. 파기된 ID의 복원은 오류다.
- 휴지통 이동 직후 폴더 수정 시각을 지금으로 정하는 것은 실패해도 무시한다(`try?`).
- 영구 삭제의 연결 정리는 살아 있는 메모와 휴지통 메모 모두에서 `modified`를 지금으로 올려 다시 쓴다. 휴지통 메모는 폴더 수정 시각을 원래 값으로 되돌린다. 메모 폴더의 수정 시각은 되돌리지 않는다.
- 영구 삭제에서 열쇠가 있거나, 휴지통 파일을 읽지 못하거나(없는 ID 포함), 잠긴 메모이면 같은 길(파기 장부 기록, 열쇠 삭제, 안전 삭제)로 간다. 없는 ID를 영구 삭제하면 파기 장부에 들어간다. Rust는 이 길을 P4로 미루고 오류로 멈춘다.
- 휴지통 비우기의 기준 시각 비교는 `폴더 수정 시각 < 기준`(같으면 남김)이고, 수정 시각을 못 읽으면 지금으로 본다. 항목별 오류는 무시한다. 앱의 보관 기간 계산은 달력 기준 일수(`Calendar.current`)라 서머타임 시간대에서는 24시간 단위와 어긋날 수 있다(Rust는 24시간 단위).
- `MemoStore`는 만들기 · 휴지통 이동 · 다시 읽기 때마다 보드 직접 순서를 정리하고, 바뀌었을 때만 `board.json`을 다시 쓴다. 본문 · 메타 저장은 `board.json`을 건드리지 않는다.
- `MemoStore.createMemo`는 `created`와 `modified`를 각각 따로 현재 시각으로 읽어 1ms 어긋날 수 있다. 시나리오는 주입 시계로 같은 값을 쓴다.
- 요약 정렬은 수정 시각 내림차순이며, 같은 시각이면 폴더를 읽은 순서에 따른다(안정 정렬이 아니다). Rust는 이름순을 유지한다. 시나리오는 시각이 겹치지 않게 짠다.
- 첨부는 이름을 정해 저장하거나 이름으로 지우는 길이 Swift에 없다(`AttachmentImages.save`는 이미지를 풀고 무작위 이름을 쓰고, 정리는 미사용 파일 일괄뿐이다). 시나리오 비교에서 Swift 실행기는 이 두 연산을 파일 직접 쓰기 · 지우기로 대신한다. 정리(`pruneUnused`)만 실제 코드를 거친다.
- 본문 검색은 `localizedCaseInsensitiveContains`이고, 골든 `search-cases.json`으로 직접 비교해 확인한 규칙은 다음과 같다(Rust는 이 규칙으로 근사, 구현은 `store/search.rs`).
  - 전체 대소문자 접기(ß = SS, ﬁ = FI, ſ = S, ẞ = ss). 터키어 ı와 İ는 접지 않고(ISPARTA는 ısparta에 안 걸림), 그리스어 아래 첨자 이오타 글자 ᾳ는 "αι"와 다르다.
  - 정규 동등(NFC = NFD)이지만 전각 영문, 반각 가타카나, 로마 숫자(Ⅳ는 iv가 아님), 분수, ™, ℓ 같은 호환 기호는 같게 보지 않는다.
  - 일치는 원래 글자 한가운데서 시작하거나 끝날 수 없다("cafe"는 "café"에 안 걸리고, "s"는 "ß"에 안 걸린다). 풀린 결합 기호만의 검색어도 완성형 글자에서는 안 걸리지만 따로 적힌 결합 기호에는 걸린다. 글자 뒤에 결합 기호, 이모지 피부색, 변이 선택자, 반각 탁점, 한글 중성 · 종성, 글자 사이 ZWJ가 이어지면 그 앞에서 끝나지 못한다. 깃발의 한쪽, ZWJ 이모지의 구성원은 따로 걸린다.
  - 숫자는 본문 쪽에서 ASCII 숫자와 같다: 십진 숫자(전각, 아랍 인도), 위 · 아래 첨자, ①, ❶, 수학용 숫자, ⑩ = "10". 단 검색어 쪽은 BMP의 십진 숫자만 접히고(검색어 ①은 본문 1에 안 걸림), 바로 앞이 문자이면 접히지 않는다("a１"은 "a1"에 안 걸림). ⒈, ⑴처럼 호환 분해에 숫자 아닌 글자가 섞인 것은 같지 않다.
  - 검색어에서 십진 숫자가 문자보다 먼저 나오면 결합 기호, 변이 선택자, ZWJ가 양쪽에서 무시된다("3e"가 "3e\u0301"에, "1"이 키캡 "1\ufe0f\u20e3"에 걸림). 이모지나 결합 기호로 시작하는 검색어는 제외된다.
  - 로케일(터키어 등)은 실행 환경 로케일에서만 확인했다. 다른 로케일의 결과는 확인하지 못했다.

## 골든과 실행

[골든 규약](../golden/README.md)에 입력 목록, 키 순서 정규화 예외, 두 구현의 CLI 계약을 기록했다. `make golden`은 기준을 갱신하고 `make test`는 기존 TestKit 러너와 `Scripts/golden-check.sh swift`를 실행한다. P2에서는 Rust 데이터 모델과 CLI가 이관한 10개 파일도 바이트 비교한다. 미이전 파일과 차분 퍼즈 사용법은 골든 규약을 따른다.

기존 테스트에서 기본 키체인을 사용하던 동기화와 백업 호출은 메모리 키체인 주입으로 보강했다. 테스트 실행기는 `CFFIXED_USER_HOME`을 임시 폴더로 지정해 Foundation 설정 저장이 실제 홈을 쓰지 않게 한다. 새 골든은 입력 폴더를 읽기만 하고, 기존 저장기 작업은 임시 폴더에서 수행한다.
