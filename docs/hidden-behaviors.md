## 요약과 실제 코드가 다른 부분

- `FileMemoRepository.saveBoardLayout`은 현재 `prettyPrinted + sortedKeys`다. 입력 객체 키 순서를 보존하지 않는다. 동작을 바꾸지 않고 현재 정렬 순서를 테스트했다.
- groups.json은 문자열 배열이다. 저장기는 `prettyPrinted`만 사용하고 배열의 원래 순서를 보존한다. 객체가 없으므로 `sortedKeys`의 효과도 없다.
- CRLF는 LF로 바뀐다. 본문의 단독 CR은 보존하지만 프론트매터 전체를 단독 CR로 구분한 파일은 현재 읽지 못한다.
- NaN은 알파 하한으로 치환되지 않고 남으며 프론트매터에는 `nan`으로 기록된다. 하한 동작은 유한 숫자에 적용된다.
- 시각 비교는 `Date.timeIntervalSince1970`의 Double로 수행한다. ±0.0005 같은 십진 경계는 Date 저장과 epoch 변환에서 표현 가능한 인접 값으로 반올림될 수 있다. 테스트는 입력 여섯 개와 실제 Double 경계를 모두 확인한다. 2001 epoch에서 ±0.0005초를 더한 값은 1970 epoch 변환 후 약 ±0.000499964초가 되어 현재 같은 순간으로 판정된다. 외부 편집의 실제 Double 경계와 바로 다음 표현 가능한 값도 별도로 확인한다. Rust도 십진수 기반의 임의 오차 보정으로 바꾸면 안 된다.
- 동기화 상태 JSON은 2001 기준 초 숫자를 사용한다. 지문 채택은 허용 오차 없이 Date의 정확한 동등 비교를 사용한다. 외부 편집 및 같은 순간 판정의 허용 오차와 별개다.

## P3에서 찾은 저장소의 숨은 동작

Rust 저장소(`mdemo-core::store`)를 Swift와 맞추며 확인한 동작이다. 시나리오 `golden/scenarios/`와 Rust 단위 테스트로 고정했다.

- 목록 읽기는 파일 앞 8KB만 읽고, 닫는 구분자 `---` 줄이 둘 미만이면 전체를 읽는다. 구분자 줄은 가로 공백만 걷어 세므로 CRLF 파일은 줄 끝 CR 때문에 하나도 세어지지 않아 항상 전체를 읽는다.
- 8KB 경계가 UTF-8 문자 한가운데에 걸리면 뒤에서 최대 3바이트를 덜어 다시 해석한다. 이 경우에는 구분자를 다시 세지 않고 앞부분만 쓰므로, 앞머리가 8KB보다 길면 그 메모는 목록에서 빠진다.
- 저장은 폴더를 먼저 만들고 파기 장부를 본다. 파기된 ID를 저장하면 오류가 나지만 빈 `memos/<ID>` 폴더가 남는다. 이때 `MemoStore.createMemo`는 저장 실패를 무시하고 요약을 목록과 보드 직접 순서에 넣고, 다음에 목록을 다시 읽을 때 빠진다.
- 휴지통 폴더가 이미 있으면 지우고 덮어쓴다. 복원 자리에 같은 ID가 있으면 복원하지 않고 오류도 없이 휴지통에 남긴다. 파기된 ID의 복원은 오류다.
- 휴지통 이동 직후 폴더 수정 시각을 지금으로 정하는 것은 실패해도 무시한다(`try?`).
- 영구 삭제의 연결 정리는 살아 있는 메모와 휴지통 메모 모두에서 `modified`를 지금으로 올려 다시 쓴다. 휴지통 메모는 폴더 수정 시각을 원래 값으로 되돌린다. 메모 폴더의 수정 시각은 되돌리지 않는다.
- 영구 삭제에서 열쇠가 있거나, 휴지통 파일을 읽지 못하거나(없는 ID 포함), 잠긴 메모이면 같은 길(파기 장부 기록, 열쇠 삭제, 안전 삭제)로 간다. 없는 ID를 영구 삭제하면 파기 장부에 들어간다. Rust는 P4에서 이 길을 옮겼다(아래 P4 항목).
- 휴지통 비우기의 기준 시각 비교는 `폴더 수정 시각 < 기준`(같으면 남김)이고, 수정 시각을 못 읽으면 지금으로 본다. 항목별 오류는 무시한다. 앱의 보관 기간 계산은 달력 기준 일수(`Calendar.current`)라 서머타임 시간대에서는 24시간 단위와 어긋날 수 있다(Rust는 24시간 단위).
- `MemoStore`는 만들기 · 휴지통 이동 · 다시 읽기 때마다 보드 직접 순서를 정리하고, 바뀌었을 때만 `board.json`을 다시 쓴다. 본문 · 메타 저장은 `board.json`을 건드리지 않는다.
- `MemoStore.createMemo`는 `created`와 `modified`를 각각 따로 현재 시각으로 읽어 1ms 어긋날 수 있다. 시나리오는 주입 시계로 같은 값을 쓴다.
- 요약 정렬은 수정 시각 내림차순이며, 같은 시각이면 폴더를 읽은 순서에 따른다(안정 정렬이 아니다). Rust는 이름순을 유지한다. 시나리오는 시각이 겹치지 않게 짠다.
- 첨부는 이름을 정해 저장하거나 이름으로 지우는 길이 Swift에 없다(`AttachmentImages.save`는 이미지를 풀고 무작위 이름을 쓰고, 정리는 미사용 파일 일괄뿐이다). 시나리오 비교에서 Swift 실행기는 이 두 연산을 파일 직접 쓰기 · 지우기로 대신한다. 정리(`pruneUnused`)만 실제 코드를 거친다.
- 본문 검색은 `localizedCaseInsensitiveContains`이고, 골든 `search-cases.json`으로 직접 비교해 확인한 규칙은 다음과 같다(Rust는 이 규칙으로 근사, 구현은 `store/search.rs`).
  - 전체 대소문자 접기(ß = SS, ﬁ = FI, ſ = S, ẞ = ss). 터키어 ı와 İ는 접지 않고(ISPARTA는 ısparta에 안 걸림), 그리스어 아래 첨자 이오타 글자 ᾳ는 "αι"와 다르다.
  - 정규 동등(NFC = NFD)이지만 전각 영문, 반각 가타카나, 로마 숫자(Ⅳ는 iv가 아님), 분수, ™, ℓ 같은 호환 기호는 같게 보지 않는다.
  - 일치는 원래 글자 한가운데서 시작하거나 끝날 수 없다("cafe"는 "café"에 안 걸리고, "s"는 "ß"에 안 걸린다). 풀린 결합 기호만의 검색어도 완성형 글자에서는 안 걸리지만 따로 적힌 결합 기호에는 걸린다. 글자 뒤에 결합 기호, 이모지 피부색, 변이 선택자, 반각 탁점, 한글 중성 · 종성, 글자 사이 ZWJ가 이어지면 그 앞에서 끝나지 못한다. 깃발의 한쪽, ZWJ 이모지의 구성원은 따로 걸린다.
  - 숫자는 본문 쪽에서 ASCII 숫자와 같다: 십진 숫자(전각, 아랍 인도), 위 · 아래 첨자, ①, ❶, 수학용 숫자, ⑩ = "10". 단 검색어 쪽은 BMP의 십진 숫자만 접히고(검색어 ①은 본문 1에 안 걸림), 바로 앞이 문자이면 접히지 않는다("a１"은 "a1"에 안 걸림). ⒈, ⑴처럼 호환 분해에 숫자 아닌 글자가 섞인 것은 같지 않다.
  - 검색어에서 십진 숫자가 문자보다 먼저 나오면 결합 기호, 변이 선택자, ZWJ가 양쪽에서 무시된다("3e"가 "3e\u0301"에, "1"이 키캡 "1\ufe0f\u20e3"에 걸림). 이모지나 결합 기호로 시작하는 검색어는 제외된다.
  - 로케일(터키어 등)은 실행 환경 로케일에서만 확인했다. 다른 로케일의 결과는 확인하지 못했다.

## P4에서 찾은 암호 메모의 숨은 동작

Rust(`mdemo-crypto`, `mdemo-core::store`의 `lock_flow` · `secure_delete`)를 Swift와 맞추며 확인했다. 시나리오 `golden/lock-scenarios/`(Swift/Rust 조합 교차)와 Rust 단위 테스트로 고정했다.

### Swift 동작 (Rust가 그대로 따름)

- 4~6자가 아니거나 영문 · 숫자가 아닌 암호로 `unlock`하면 `wrongPassword`를 돌려주지만 시도로 세지 않는다(열쇠 저장소도 앞머리도 그대로). 형식이 맞는 틀린 암호만 센다.
- 실패 횟수는 `max(앞머리 lockFailures, 열쇠 저장소 failures)`에서 시작한다. 앞머리의 음수는 무시된다. 이 값이 10 이상이면 암호가 맞아도 열지 않고 바로 파기한다. 저장소 횟수 글자는 `Int` 파싱이라 `+7`, `-0`도 받고, 음수 · 비정수 · UTF-8이 아니면 `damaged`다(`unlock`은 이때 열쇠를 읽기 전에 오류로 끝난다).
- 시도 전에 저장소에 `failures + 1`을 쓴다. 키 유도나 열쇠 복호 도중 태그 불일치(틀린 암호)가 아닌 오류가 나면 `failures`로 되돌리고 오류를 그대로 올린다. 틀린 암호이면 저장소는 `failures + 1`로 남고 앞머리도 같은 값으로 저장한다. 앞머리 저장이 실패하면 그 오류가 `wrongPassword` 대신 올라간다.
- 열쇠(KEK로 연 감싼 열쇠)는 맞는데 본문이 손상되면(태그 불일치 · base64 아님 · UTF-8 아님) `damaged`이고 횟수는 시도 전 값으로 되돌려질 뿐 0으로 초기화되지 않는다. 0 초기화(저장소 먼저, 그 다음 앞머리 저장)는 본문 검증까지 마친 성공 때만 한다.
- 태그 불일치는 `unlock`에서만 `damaged`로 바뀐다. `decryptedDocument`, 첨부 읽기, `moveToPlainMemo`에서는 `MemoLockError`가 아니라 CryptoKit 오류(`authenticationFailure`)가 그대로 올라온다. 첨부가 하나라도 손상되면 `moveToPlainMemo`는 중단하고 새 폴더를 안전 삭제하지만 잠긴 메모와 열쇠는 그대로다. 열 때(`unlock`)는 첨부를 검사하지 않는다.
- `createLockedMemo`: 새 메모의 `isOpen`을 항상 true로 만들고, 제목은 직접 붙인 제목만(공백만 있으면 버리고 앞뒤 공백은 지우지 않고) 가져오며 링크 · 충돌 표시 · 알 수 없는 링크 토큰은 비운다. 알 수 없는 앞머리 줄(`unknownFrontmatterLines`)은 원본에서 그대로 새 잠긴 메모의 평문 앞머리로 넘어간다(암호 밖에 남는다).
- `createLockedMemo` 순서: 열쇠 저장소에 감싼 열쇠 쓰기, `local-only` 장부 기록, 본문 암호화 저장, 첨부 암호화 후 즉시 개봉 검증, 원본 재확인, fsync, 열쇠 저장소에서 다시 읽어 키 유도를 한 번 더 해 본문 · 첨부 해시를 대조한 뒤 원본을 파기한다. 중간에 실패하면 열쇠와 새 폴더만 지우고(`try?`) 장부에 오른 `local-only` ID는 되돌리지 않는다. 키 유도는 만들 때 두 번 한다.
- `changePassword`는 새 솔트 · 반복 횟수로 열쇠를 다시 감싸고 실패 횟수 · 수정 시각은 그대로 둔다. 열쇠 저장은 앞머리 저장보다 먼저라서, 앞머리 저장이 실패하면 이전 열쇠를 되돌려 쓴다.
- `relock`은 잠긴 메모가 아니어도 요약의 미리보기를 비운다. `moveToTrash`는 모든 메모에 `relock`을 부른다(휴지통으로 가는 메모는 목록에서 곧 빠져 보이지 않는다).
- `destroyMemo` 순서: 열쇠 + 실패 횟수 삭제, `relock`, `destroyed` 장부 기록, (시험 주입 지점), 메모 폴더 · 휴지통 폴더 안전 삭제, `repository.permanentlyDelete`(같은 길을 한 번 더 타고 연결 정리), 요약 · 연결 · 보드 배치와 벤토 크기 정리, `board.json`을 항상 다시 씀. `onPrivacyChange`는 장부 기록 이후에는 오류로 끝나도 부른다.
- 휴지통 비우기(전체 · 기간)는 잠긴 항목을 `destroyMemo`로 먼저 파기한다(오류 무시). 기간 비우기에서 버린 시각을 읽지 못한 잠긴 항목은 파기하지 않는다(`distantFuture`).
- 파일에 열쇠가 없어도 앞머리가 잠금이면 영구 삭제는 장부 + 안전 삭제 길을 탄다. 그리고 `permanentlyDelete`의 열쇠 확인(`keychain.read`)이 오류면 아무것도 지우지 않는다.
- 안전 삭제는 일반 파일마다 같은 길이의 난수로 덮고 fsync하고 크기 0으로 줄이며, 심볼릭 링크는 건드리지 않는다(그 아래로도 안 들어간다). 쓰기 권한이 없는 파일이 하나라도 있으면 아무것도 지우기 전에 오류다. `synchronize`는 심볼릭 링크를 만나면 `damaged`다. 숨김 파일도 포함한다.
- 잠긴 메모를 저장하면(앞머리 저장 포함) 메모 폴더에 백업 제외 표시를 단다. 달지 못하면 저장 자체가 실패한다.
- 장부 `MemoPrivacyLedger.write`는 합집합 · 정렬 · 임시 파일 fsync · 교체이며 읽을 수 없는 장부는 오류다.

### Rust에서 다른 점 (맞출 수 없거나 확신이 없는 부분)

- `unlock` · `createLockedMemo` · `changePassword`는 동기 함수다. Swift의 백그라운드(`Task.detached`)와 `unlocking` 중복 방지(`locked`를 던짐)는 두지 않았다. P7에서 호출 쪽이 백그라운드를 정한다.
- `calibratedIterations`: Swift는 `CCCalibratePBKDF`, Rust는 20만 회를 직접 재서 500ms로 환산한다. 값은 기기마다 다르며 앞머리에 저장되므로 호환에는 영향이 없다. 범위(200만~2천만)는 같다.
- 안전 삭제는 Swift의 `O_NOFOLLOW` 대신 열기 전에 `symlink_metadata`로 종류를 확인한다. 확인과 열기 사이에 파일을 링크로 바꾸는 경쟁은 막지 못한다. Windows는 폴더 fsync를 하지 않는다(P8에서 정한다).
- 백업 제외는 맞춤: 맥에서는 같은 확장 속성(`com_apple_backup_excludeItem`)을 `setxattr`(unsafe 한 곳)로 같은 바이트로 쓴다. Windows는 아직 표시가 없다(P8).
- 암호 오류 이름: Swift `CryptoKitError.authenticationFailure` · `incorrectParameterSize`는 `StoreError::Authentication` · `IncorrectSize`로 나뉘어 남는다(`damaged`로 합치지 않는다).
- Swift `MemoLockError.keychain(OSStatus)`는 `KeyStore(String)`이다. 난수 생성 실패도 Swift처럼 여기로 모은다.
- Swift 테스트 `새 암호 메모의 첫 저장 · 편집은 암호문이고 ... 백업 제외` 실패(기록된 환경 제약)는 이 환경의 임시 폴더에서는 재현되지 않았다(`isExcludedFromBackup`을 설정하고 읽으면 true). 시나리오가 두 구현의 표시 유무를 비교한다.

### 비밀 다루기와 한계 (`mdemo-crypto`)

- 열쇠 · KEK · 암호 가공물 · 복호화한 본문은 `Zeroizing<Vec<u8>>`에 둔다. 고정 길이 배열은 옮길 때 복사본이 남아 쓰지 않았다. 세션의 열쇠는 `clear()`와 떨어질 때 0으로 덮는다. 공개 API는 암호를 `&[u8]`로 받는다.
- `seal`은 출력 버퍼에 평문을 넣고 제자리에서 암호화한다(평문 별도 복사본 없음). `open`은 암호문을 `Zeroizing` 버퍼에 복사해 제자리에서 풀고 그대로 돌려준다(AES-GCM은 태그 확인 뒤에 푼다).
- 검사: (1) 해제되는 블록의 내용을 들여다보는 시험용 전역 할당기로, 감시하는 크기의 `Zeroizing` 버퍼와 `open` 결과가 0으로 해제되는지(보통 `Vec`은 더러운 채 해제되는 것을 같은 방법으로 보여 감시기가 동작함을 확인), (2) 세션 `clear()` 뒤 열쇠 버퍼 용량 전체가 0인지 직접 소유한 포인터로 확인한다. 한계: 감시는 정해 둔 크기의 블록만 보고(같은 크기의 다른 할당과 섞이면 구별 못 함), 레지스터 · 스택 · 커널 · 페이지 캐시에 남은 사본, 스왑, 코어 덤프는 검사하지 못한다.
- 우리가 덮을 수 없는 곳: PBKDF2의 `hmac`/`sha2` 내부 상태(암호에서 만든 패드 블록)는 해당 크레이트가 덮지 않는다. AES 라운드 키와 GHASH 키는 `aes-gcm`의 `zeroize` 기능에 맡겼고(문서화된 보장) 우리 시험은 확인하지 않는다. `fs::read`가 파일이 읽는 도중 커져 버퍼를 다시 잡으면 앞의 버퍼는 덮이지 않고 해제된다(현재 경로는 크기를 미리 알고 있어 발생하지 않는다).
- 평문이 `String`으로 남는 곳(`lock_flow.rs` 머리말에도 있다): 일반 메모를 잠글 때 읽는 원본 `MemoDocument.body`와 비교용 재읽기 복사본(떨어질 때 덮음, 원본이 이미 평문 파일), 잠금을 일반 메모로 옮길 때의 `MemoDocument.body`(쓰고 나서 덮음)와 `frontmatter::encode`가 내부에서 만드는 임시 문자열(덮을 수 없음), `save_body(&str)`로 들어오는 본문(호출자 소유). 시나리오 실행기는 시험 도구라 암호를 JSON 문자열로 든다.
- 코드 검토 목록: `mdemo-crypto` 안에서 비밀 바이트가 `Zeroizing`이 아닌 그릇에 들어가는 곳은 `seal`의 반환 버퍼(암호문으로 바뀐 뒤 반환)와 `KeyStore`의 감싼 열쇠(암호문)뿐이다.

## P5에서 찾은 마크다운 엔진의 숨은 동작

`mdemo-markdown`(Rust)은 아래 동작까지 Swift와 바이트 단위로 맞췄다(골든 `markdown-cases.json` 사례 1,280여 건과 차분 퍼즈). 모두 Swift 구현을 바꾸지 않고 그대로 따른 것이다.

- **`Character ==`는 정규 동치다.** U+1FEF(그리스 바리아)는 `` ` ``와, U+037E는 `;`와, U+212A(켈빈)는 `K`와, U+0387은 `·`와 같다. 그래서 U+1FEF 두 개가 인라인 코드 기호 구실을 하고, OCR 줄머리의 U+0387이 글머리 `·`로 읽힌다. 한글 자모 열과 완성형도 같다.
- **`hasPrefix` · `hasSuffix` · `contains`는 문자소 경계에서만 맞는다.** `-` 바로 뒤에 결합 기호가 붙은 줄(`-\u{301} x`)은 글머리가 아니고, 닫는 `)` 뒤에 결합 기호가 붙은 줄은 이미지 줄이 아니다. 첨부 경로의 `/` 뒤에 결합 기호가 붙으면 그 글자는 `/`로 세지 않아 파일 이름으로 통한다(`attachments/a/\u{301}.png`는 유효한 이미지).
- **`replacingOccurrences`는 스칼라 단위로 찾되, 일치 바로 뒤에 결합 기호(Extend: 결합 악센트, 변이 선택자, 이모지 피부색, ZWNJ)가 붙은 자리는 건너뛴다.** 그래서 `\r\n` 뒤에 `\u{FE0F}` 같은 글자가 오면 `\r\n`이 `\n`으로 바뀌지 않고, 뒤이은 `\r` 바꾸기가 `\r\n` 가운데의 `\r`만 `\n`으로 바꾼다. ZWJ · 간격 결합 기호 · 한글 자모가 뒤따르는 자리는 바꾼다. 앞쪽 글자는 상관없다. NBSP 바꾸기도 같다.
- **`components(separatedBy: "\n")`은 스칼라마다 자른다.** `\r\n` 한가운데의 `\n`에서도 자르고(`\r`은 앞 줄에 남는다), 뒤에 결합 기호가 붙어도 자른다. (같은 함수를 문자소 경계로 쓰는 `frontmatter` 쪽 분리와는 다르다.)
- **들여쓰기 한 칸짜리 제목.** 들여쓰기 단계는 `공백 수 / 2`라 공백 한 칸은 0단계이고, 앞 공백을 뗀 줄이 `# `로 시작하면 제목이다(` # 제목`은 제목 1).
- **`Character.isNumber`는 첫 스칼라의 Numeric_Type이 None이 아닌지만 본다.** 한자 숫자(`一`), 분수(`½`), 동그라미 숫자, 아랍 인도 숫자, 숫자 + 결합 기호가 모두 숫자다. 붙여넣기의 `isListLine` · `1)` 변환은 이 글자들도 번호로 보지만(`一) 항목` → `一. 항목`), 해석기는 `Int(...)`가 읽는 ASCII 숫자만 번호 목록으로 받아 결과는 문단이다. 자리수가 `Int`를 넘는 번호(`99999999999999999999.`)도 문단이다. 입력 규칙의 `1.` 규칙도 같다.
- **이미지 줄 정규식(ICU)**: `\s`는 White_Space(NBSP · NEL · 줄 구분자 · VT 포함, ZWSP는 아님), `\d`는 Nd다. `=너비`가 ASCII 숫자가 아니거나(`=٣`) `Int` 범위를 넘거나 0이면 이미지가 아니라 문단이다. `\u{2028}`로 경로와 `=너비`를 띄운 줄은 이미지다.
- **색 태그 길이는 문자소로 센다.** 여는 태그의 `>` 바로 뒤에 결합 기호가 붙어 있으면 `>`와 결합 기호가 한 글자(`Character`)라 태그가 그것까지 삼킨다. `<span style="color:#D93025">\u{301}x</span>`는 `\u{301}`이 사라진 `x`가 된다(글자 하나가 조용히 없어짐). 닫는 태그 뒤 결합 기호는 닫는 태그가 `Character` 하나로 안 맞아 서식 없이 글자로 남는다.
- **`lowercased()`는 글자마다 대응하며 마지막 시그마 문맥이 없다.** 슬래시 명령 검색에서 `ΑΣ`는 `ας`가 아니라 `ασ`가 된다. Rust의 `str::to_lowercase`는 문맥을 보므로 글자별 `char::to_lowercase`로 맞췄다.
- **슬래시 명령 검색은 로케일을 쓰지 않는다.** `lowercased()` · `hasPrefix` · `contains`뿐이라 검색 판정(`localizedCaseInsensitiveContains`)과 달리 Rust가 정확히 따라간다. 그래서 마크다운 엔진은 전부 Rust로 옮길 수 있고 맥에 남길 부분이 없다.
- **입력 규칙의 위치는 Character 단위다**(UTF-16이 아니다). `caretOffset`, 돌려주는 구간 모두 같다. 화면(NSTextView)이 UTF-16을 쓰면 연결하는 쪽(P7)에서 바꿔야 한다.

한계: 이 비교는 macOS 26.6.2(Xcode 27.0)의 Swift · Foundation · ICU로 만든 기준이다. Rust는 Unicode 17.0 표(숫자 종류는 `Scripts/generate-markdown-tables.py`, 정규 분해는 mdemo-core, 문자소 경계는 `unicode-segmentation`)를 쓴다. 앱이 지원하는 하위 macOS(14)의 Swift 런타임과 Foundation은 유니코드 판이나 문자열 함수 구현이 달라 새로 배정된 글자나 위의 Foundation 관찰이 다를 수 있다. 확인하지 못했다.

## 골든과 실행

[골든 규약](../golden/README.md)에 입력 목록, 키 순서 정규화 예외, 두 구현의 CLI 계약을 기록했다. `make golden`은 기준을 갱신하고 `make test`는 기존 TestKit 러너와 `Scripts/golden-check.sh swift`를 실행한다. P2에서는 Rust 데이터 모델과 CLI가 이관한 10개 파일도 바이트 비교한다. 미이전 파일과 차분 퍼즈 사용법은 골든 규약을 따른다.

기존 테스트에서 기본 키체인을 사용하던 동기화와 백업 호출은 메모리 키체인 주입으로 보강했다. 테스트 실행기는 `CFFIXED_USER_HOME`을 임시 폴더로 지정해 Foundation 설정 저장이 실제 홈을 쓰지 않게 한다. 새 골든은 입력 폴더를 읽기만 하고, 기존 저장기 작업은 임시 폴더에서 수행한다.

## P6 동기화 · 백업에서 확인한 규칙

- SyncService 지문은 첨부를 포함한 폴더가 아니라 `memo.md` 바이트의 SHA-256이다. 첨부만 바꾸면 엔진의 메모 변경 판정은 바뀌지 않는다. 전송할 때는 폴더 전체를 교체하며, 드라이브 거울은 파일별 MD5를 사용한다.
- 외부 편집은 1970년 기준 Double로 `modified <= last + 0.0005`, 같은 순간은 차이의 절댓값 `< 0.0005`로 판단한다. 정확한 경계에서는 Double 덧셈의 반올림도 Swift와 같아야 한다. 상태 쌍 날짜는 허용 오차 없이 `==`다.
- 외부 편집본을 로컬에서 보내면 원본 앞머리도 고친다. 원격에서 받으면 원격 앞머리를 고치지 않고 수신본만 고치므로 상태에는 두 지문이 남을 수 있다. 훑은 뒤 어느 쪽 지문이 바뀌면 사본도 만들지 않고 다음 회차로 넘긴다.
- 한쪽 파일이 단순히 사라지면 SyncService는 남은 쪽을 다시 보낸다. 휴지통 전파와 파기 장부는 별도 경로다. 드라이브에서 파일이 사라지면 거울에서는 지우지만, 데이터에 남은 메모는 엔진이 다시 올릴 수 있다. 기존 Swift 규칙을 유지했다.
- 드라이브의 완료 표시는 내려받기만으로 켜지지 않는다. 올리기 · 파일 삭제가 모두 성공해야 켜진다. 실패한 파일 요청은 상태를 확정하지 않아 재시도한다. update의 notFound는 새 upload로, delete의 notFound는 성공으로 처리한다. 빈 폴더 삭제 실패는 완료 여부에 영향을 주지 않는다.
- 첫 회차에도 개인정보 purge 항목은 영구 삭제할 수 있다. 목록 또는 내려받기 중 하나라도 실패하면 엔진과 올리기 단계에는 진입하지 않는다. 기본 5번은 삭제 예정 항목과 다운로드 변경 항목을 함께 둔 실패 회차도 확인한다.
- macOS Foundation의 거울 파일 경로는 한글을 정규 분해한 이름으로 만들 수 있다. Rust macOS 거울 훑기도 같은 이름으로 요청한다. 첨부 내용은 그대로 유지한다.
- 백업 내보내기는 허용된 메모 폴더 안 숨김 파일도 보존한다. 가져오기 합치기는 memos · trash의 숨김 항목을 건너뛰고 같은 ID를 덮어쓰지 않는다. 합치기는 groups · board · local-only를 덮어쓰지 않으며 destroyed만 합친다.
- ditto ZIP은 UTF-8 한글 파일명에도 언어 비트를 생략할 수 있다. Rust는 원시 파일명이 유효한 UTF-8이면 그대로 읽고 `__MACOSX`는 건너뛴다. ZIP 바이트와 리소스 포크는 백업 동치의 대상이 아니다.
- 백업 교체에서도 현재 기기의 잠긴 메모는 암호문 폴더와 백업 제외 표시를 보존한다. 파기 장부는 복원 전에 합치고 기존 사본 · 열쇠부터 지운다. 파기 ID는 가져오기 결과의 건너뛴 수에 ID별로 한 번만 센다.
- Rust의 폴더 복사와 ZIP 가져오기는 심볼릭 링크, ZIP 상위 경로 이동, Windows 구분자와 드라이브 접두사를 거부한다. Swift의 ditto 경로까지 바꾸지는 않았다.

- macOS 27 검증 환경에서 `URLResourceValues.isExcludedFromBackup` 조회는 표시를 설정한 직후에도 false를 돌려준다. 같은 폴더의 `com.apple.metadata:com_apple_backup_excludeItem`에는 `com.apple.backupd` 속성 목록이 실제로 있다. 기존 MemoCore 테스트는 조회 결과 대신 디스크의 속성 목록 값을 검증하도록 바꿨고 Swift 앱 저장 코드는 유지했다.

## P7 그림자 비교 계약

Swift `FileMemoRepository`가 실제 데이터 폴더를 쓴다. Rust의 실제 폴더 접근은 `read_only` 생성 경로의 읽기뿐이다. 쓰기 비교는 실제 폴더 밖 `Shadow/<회차>/before`에만 적용하고, Swift 결과의 `after` 복제본과 비교한 뒤 회차 폴더를 지운다. 기본값은 꺼짐이며 `MDemoRustShadow` Bool 또는 `--rust-shadow`로 켠다. 기본 경로는 `Application Support/MDemo/Shadow`, `--data-dir=X`일 때는 정규화한 X의 부모 아래 `<X이름>-shadow`다.

요약 해시의 정규 문자열 정의는 이 절을 기준으로 한다. 메타데이터만 가진 `MemoDocument(meta, body: "", unknownFrontmatterLines: [], unknownLinkTokens: [])`를 각 구현의 프론트매터 저장기로 직렬화한다. 여는 구분자와 닫는 구분자, 빈 본문 앞 마지막 LF도 포함한다. 그 UTF-8 문자열에 NUL 한 개, 미리보기, NUL 한 개, `deletedAt.timeIntervalSinceReferenceDate`의 Swift `String(describing:)` 표기를 차례로 붙인다. 삭제 시각이 없으면 마지막 문자열은 빈 문자열이다. 전체 UTF-8 바이트의 소문자 SHA-256을 비교하며 목록 순서는 비교하지 않는다. 정수 Double은 `800000000.0`, 작은 값의 지수는 `1e-05` 형식이다.

트리 비교는 숨김 파일, 첨부, 빈 폴더와 최상위 폴더를 포함한다. 폴더는 `dir:` 접두사, 링크는 SHA-256 필드의 `link` 표지로 구별하며 링크를 따라가지 않는다. 복제 경로에 링크가 있으면 Swift 측에서 해당 회차를 생략한다. mtime은 2001 기준 Double이며 절댓값 차이 1µs 이하만 같은 것으로 본다. 명시적으로 기록하는 휴지통 폴더 시각은 Swift 결과에서 읽어 Rust ManualClock에 전달한다. 영구 삭제와 비우기는 연결이 실제 바뀐 결과의 modified를 시계에 전달한다.

mtime은 저장소가 시각을 직접 정하는 휴지통 폴더(`dir:trash/<ID>`, 삭제 시각)만 1µs 이하로 비교한다. 그 밖의 파일 · 폴더 mtime은 파일 시스템이 쓰는 순간을 찍으므로 독립된 두 저장에서 같을 수 없어 바이트 · 크기만 비교한다(P3 시나리오 비교의 휴지통 폴더 시각 규칙과 같다). 여러 연결을 지우는 중 Swift 시계가 밀리초 경계를 넘으면 결과 modified가 여러 값일 수 있다. 현재 단일 ManualClock에는 바뀐 결과 중 가장 큰 값을 전달하므로 이때의 바이트 차이도 기록된다.

잠긴 입력이나 영향 경로의 잠긴 메모는 복제 전에 생략한다. 여러 잠긴 메모가 걸린 호출은 잠긴 ID별 해시 기록을 남긴다. 영구 삭제는 대상과 그 대상으로 향하는 연결을 가진 메모 폴더, 두 개인정보 장부만 복제한다. 전체 휴지통 비우기도 만료 대상과 연결 영향 경로만 복제한다. 검색, 첨부 경로 조회, 첨부 정리는 Swift에 그대로 위임한다.

기록에는 원래 ID, 제목, 본문, 그룹 이름, 오류 문장을 쓰지 않는다. ID와 임의 파일명은 SHA-256 앞 12자만 남긴다. 차이 기록에는 경로별 두 해시, 크기, mtime을 넣고 누락 항목은 null로 쓴다. 읽기 차이는 Swift와 Rust를 한 번 더 읽고, 그사이 Swift 결과도 바뀌면 `skipped: changed`로 남긴다. 요약 비교는 각 목록 종류별 시작 시 한 번과 이후 한 시간에 최대 한 번이다. 기록 요약은 재시작 후에도 누적한다.

작업 용량은 두 복제본과 새 입력의 예약량으로 제한한다. 500MiB 또는 대기 중인 비교 200건 상한에 걸리면 실제 Swift 호출은 실행하고 `skipped: backlog`를 기록한다. 정리하지 못한 회차의 예약량은 계속 상한에 포함한다. 기록 자체의 디스크 오류는 앱에 전파하지 않는다. 메인 호출 경로에는 복제뿐 아니라 잠금 헤더 확인과 링크·용량 메타데이터 검사도 필요하다. 본문 해시, Rust 연산과 비교, 기록은 직렬 utility 큐에서 수행한다.

잠금 여부를 판단할 앞머리를 읽지 못하거나 메모 폴더가 링크이면 복제하지 않고 `skipped: unreadable`로 남긴다. `memos`·`trash` 자체가 링크인 저장소에는 장식자를 설치하지 않는다. 읽기 차이의 경로는 `memos/<ID해시>/memo.md` 또는 `<memos|trash>/<ID해시>/summary`이며, API가 해시만 돌려주는 정규 문자열의 크기·mtime은 null로 명시한다.

### P7 그림자 실행에서 찾은 차이: 파일 시각 변환 순서

Foundation은 파일 수정 시각을 `(tv_sec - 978307200) + tv_nsec * 1e-9` 순서로 2001 기준 Double로 바꾼다. Rust는 1970 기준 실수(`as_secs_f64`)에서 978307200을 빼서 마지막 자리가 달랐다. 실제 휴지통 10개 중 4개의 `deletedAt`이 1ulp 어긋났다(P3 시나리오는 밀리초 반올림 비교라 놓쳤다). `from_system_time`을 Foundation 순서로 고치고 실제로 어긋났던 값으로 회귀 시험을 넣었다.

### P7 빠른 그림자 검사에서 정한 비교 규칙

`Scripts/shadow-exercise.sh`(실제 데이터 복제본, 무작위 MemoStore 연산)로 찾은 차이는 모두 비교 도구가 Rust에 넘기는 입력의 문제였고 저장 규칙 차이는 없었다. 그래서 그림자 연산에 다음을 넘긴다.
- 저장 · 복제: 파일 글자 외에 Swift 문서의 `created` · `modified`(2001 기준 Double)와 본문을 그대로 넘긴다. 파일은 밀리초까지라 다시 읽으면 마지막 밀리초가 내려가고(P2 기록, 두 구현 같음), 본문의 `\r\n`은 다시 읽을 때 정리된다.
- 영구 삭제 · 비우기: Swift는 연결을 지울 메모마다 그때 시계를 찍어 밀리초가 서로 다를 수 있다. 메모별 modified(파일 값 + 0.4ms, 밀리초 내림 직렬화가 같은 글자를 내도록)를 넘겨 Rust 연산 뒤 그 값으로 맞추고 나머지 바이트를 비교한다.
- 읽기 비교 도중 이 저장소로 쓰기가 있었으면(휴지통 이동 · 복원 등) 오류가 아니라 `skipped: changed`로 센다.
